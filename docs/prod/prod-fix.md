# 生产问题排查
## OOM排查
linux环境下排查思路：  
通过命令top命令
```shell
top
```
或者ps命令
```shell
ps aux --sort=-%mem head -n 11 
```
以上两个查看命令内存占用排序  
ps aux：显示所有进程的详细信息。  
a：显示所有终端上的进程。  
u：以用户友好的格式输出。  
x：包括不连接终端的进程。  
--sort=-%cpu：按 CPU 使用率降序排列（- 表示降序）。  
--sort=-%mem：按内存使用率降序排列。  
head -n 11：输出前 11 行（第 1 行是标题，后面 10 行是数据）。  

定位到具体高占用进程pid之后
通过top命令

```shell
top -H -p <pid>
```

先别重启应用，首先dump堆，解析堆快照

```shell
jmap -dump:format=b,file=<filename>.dump <pid>
```

OOM可能原因：
- 内存泄露
- 资源正常没关闭
- 配置不合理
- 线程数过多，递归调用太深

## CPU100%
top 或ps命令查看cpu占用排序高的进程

jps命令查看pid
```shell
jps -v
```
threaddump
```shell
jstack [-l] <pid> | tee -a jstack.log
```

可能原因：
- 死循坏（while、无限递归）
- 死锁，两个资源都在等待对方释放锁资源
- 大量计算密集型任务同一个时间占用
- 大量并发线程，导致cpu频繁切换
- 大量上下文切换，导致cpu性能下降
- 内存不足导致使用虚拟内存，虚拟内存的运行速度慢很多
- 频繁GC
- 内存泄露->可用内存减少->导致频繁GC->最终OOM

## 接口响应慢怎么排查、怎么优化
1、问题定位  
首先确认
- 偶发性还是持续性？  
- 单个接口慢还是整体系统慢？  
- 是否与特点时间高峰期有关？  
- 是否与特定特务场景和请求参数有关？  

偶发情况: 服务端初始化耗时（如OpenFeign首次调用耗时、Redis热点数据没有预热）、频繁GC
持续情况：
单个接口慢：从代码层开始排查入手，是否有循环调用、第三方跨服务/超时、慢SQL等情况出现。 
整体系统慢：
网络延迟 -> 走静态资源CDN、文件服务器分离  
数据库MySQL负载是否有慢sql占用大量cpu内存资源阻塞其他正常请求 -> 优化SQL、数据库本身配置或者是否需要分库分表、监控mysql、慢sql及时告警    
Redis缓存穿透、击穿、雪崩等情况、或者是遍历大key及热点key问题 -> 客户端本地缓存+Redis缓存，减少穿透，热点数据预热加载  
jvm是否内存泄露、jvm频繁GC导致cpu资源浪费在gc上，如大对象直接晋升的内存区域太小
操作系统瓶颈：
并发量确实比较大，硬件资源不足
是有存在死锁或多锁竞争、是否存在线程数过多情况导致cpu资源浪费在线程切换上  

## 接口响应慢怎么优化
1、网络层面
网络延迟
解决方案：网络链路优化，跨地域部署CDN或边缘节点缩短物理距离、关键业务走vpc避开公网堵塞
前端资源多、一次性加载过多内容或接口
解决方案：资源懒加载、前端静态CDN加速  
2、应用层面
代码优化 ->避免循环调用、大事务或一次性大数据集查询等  
跨服务调用超时 -> 异步化改造，将非核心操作解耦由消息队列补偿执行  
3、数据库层面
SQL索引优化
数据库配置优化 -> 数据库连接数、缓冲池  
单表数据量过大 -> 读写分离、分库分表等  
4、中间件层面
Redis缓存穿透、击穿、雪崩导致mysql满载  
解决方案：  
1：缓存穿透：参数校验 -> 布隆过滤器-> 空值短时过期缓存
2：缓存击穿：加锁读取，无锁降级，防止高并发打满数据库
3、缓存雪崩：过期时间添加随机TTL，让过期时间短时间随机分布

## JMM Java Memory Model Java内存模型
三大特性：原子性，可见性，有序性
主内存-> 线程工作内存 -> 线程
CAS,AQS
AQS不保证公平，有可能存在新线程插队情况

## 双亲委派机制
从上到下 BootStrap -> Extension -> Application
当收到类加载任务时，从下向上询问父类加载器是否加载过，如果是，则放弃加载，否则从上到下尝试加载
避免多次重复加载以及覆盖JDK核心类库
